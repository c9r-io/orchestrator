# FR-160: QA harness 的守护进程拆解 —— `wait` 在 23 个门禁里是空操作

## 优先级: P2

## 状态: Proposed

## 背景

所有计数 at `e48fc1b5`，方法逐条注明。

FR-158 收尾时，CI run `30795701182` 的 governance job 变红在 `parity` 上，而该门禁自己的输出是 `FR-126 production parity: 11 passed, 0 failed`。失败发生在断言**之后**的 EXIT trap 里：`rm -rf "$QA_ROOT"` 撞上仍在写入 `data/` 的进程，返回 `Directory not empty`，该退出码成了整个 step 的退出码。日志里没有任何东西把这次失败和门禁测的东西连起来。

即时症状已由 `e48fc1b5` 挡住（cleanup 失败不再覆盖门禁的判决，且改动覆盖了当时找到的全部三处）。本 FR 处理的是**下面那层**——为什么 `rm` 会撞上一个本该已经退出的守护进程。

### 实测到的机制

cleanup 的形状是 `kill "$DAEMON_PID"` 然后 `wait "$DAEMON_PID"`。`wait` 只对**当前 shell 的子进程**有效；从 pidfile 读回来的 PID 通常不是——守护进程是在子 shell 里启动的，PID 经由文件传递。

用一个捕获 SIGTERM 后需要 2 秒才退出的假守护进程复现两种形状（探针脚本见「验证方法」）：

| 形状 | `wait` 返回耗时 | 返回后守护进程 | 它的文件 |
|---|---|---|---|
| pidfile（`DAEMON_PID="$(<...daemon.pid)"`） | **0s** | **仍存活** | **仍存在** |
| 直接子进程（`DAEMON_PID=$!`） | 2s | 已退出 | 已删除 |

所以在 pidfile 形状里，`wait` 立即返回，cleanup 紧接着对一个**活着的写入者**执行 `rm -rf`。这不是偶发的时序问题，是这段代码在该形状下的常态行为；`Directory not empty` 只在守护进程恰好还在写盘时才浮现，所以它表现为偶发。

### 规模

- **25 个**受追踪的 `scripts/**/*.sh` 用单 PID kill 守护进程。方法：`git ls-files 'scripts/**/*.sh'` 逐个 grep `kill "$…PID"`（单一方法，见下方交叉核验说明）。
- 其中 **23 个**从 pidfile 取 PID（`DAEMON_PID="$(<…)"` 或 `"$(cat …)"`），**2 个**用 `$!`。方法：对赋值行的形状分类，两类相加等于 25，无未分类项。
- 按 enforcement 分：**3 个 ci-required、22 个 manual-runbook**（方法：逐路径查 `qa-gate-surface.json`）。

> **交叉核验说明（重要）**：第二条独立推导（grep 背景启动 `_PID="?\$!`）给出 6 个文件，与 25 不符。核实后两者并不矛盾——那 6 个里多数是 **session PID** 而非守护进程 PID 的赋值，`$!` 在这些脚本里另有用途。分歧本身是有价值的：它说明"从 `$!` 取 PID"在仓库里同时服务两个不同的对象，任何按这个模式做的批量改写都会误伤。25 与 23/2 的拆分是按 `DAEMON_PID` 赋值行分类得到的，这是目前唯一自洽的口径。

### 这是一次被记成全局的局部修复

FR-159 **已经发现过这个缺陷**，其闭环记录写着：「`stop_daemon` also never waited — the daemon is a subshell's child, so `wait` on it returned immediately, and both daemons share one PID file」。它在 `test-agent-session-control-plane.sh` 里写出了正确的处置（`reclaim_recorded_sessions` / `reclaim_previous_run_residue`：记录每个 session PID、按进程组回收、启动时清扫上一轮残留）。

那套函数**只存在于那一个文件里**（方法：`rg -l 'reclaim_recorded_sessions|reclaim_previous_run_residue' scripts/` 返回单个路径）。没有被提取，另外 24 个没有被改。

这正是 §4.4 shape 9 的形状，与 FR-134「三处改完、CHANGELOG 写下 *every such pipeline in the governance scripts is now a here-string*、实际还剩 61 处」同源。FR-159 的记录本身没有过度声明（它说的是「stop_daemon」这一处），所以这里**不需要更正任何既有陈述**——需要的是把修复推到其余站点。

### 代价

FR-159 实测（**引自 DD-171，本 FR 未重新推导**）：开发机上 28 个存活 19 天的 fixture 会话进程、133.7 小时累计 CPU、18102 个临时文件约 12GB。这些泄漏的来源是 QA harness，而 harness 的守护进程拆解正是本 FR 的对象。

CI 侧代价是另一回事：runner 用完即弃，所以那里的成本不是资源而是**假红**——一个通过的门禁被 cleanup 的退出码染红，且 22 个 manual-runbook 门禁根本不在 CI 里跑，它们的泄漏只落在人的机器上。

### 治理事故记录（2026-08-10 增补）

第一次治理本 FR 的会话（2026-08-03 晚之后）以开发机文件系统故障告终：机器无法重启进入系统，2026-08-05 16:48 macOS 全新重装（`.AppleSetupDone` 时间戳），19:58 本仓库重新 clone。可确认的事实：

- **治理成果全部丢失。** main 上本 FR 的最后一次提交是立项文档本身（`4e1a44b2`），无 stash、无本地或远程工作分支、`~/.orchestratord` 不存在。共享拆解库与 25 个站点的迁移需从零重做。
- **故障的直接机制不可核验。** 旧文件系统随重装销毁，无日志、无残留可查。不能排除与本仓库无关的原因（操作系统或硬件）。
- **可核验的是暴露面。** 治理动作要求在一台已带 DD-171 实测存量泄漏（约 12GB、18102 个临时文件、28 个存活进程）的机器上，密集重跑全部 25 个泄漏源——包括平时从不运行的 22 个 manual-runbook 门禁，且复现探针要求刻意制造不被回收的守护进程。病因先于治理存在；急性放大发生在治理会话中，是当时证据下的最合理推断，非已证结论。

### 治理前置条件（由上述事故导出）

重新治理时按以下顺序与防护执行，顺序本身就是防护：

1. **先做需求 1 的共享库并单独验证**，再触碰 25 个站点。不得为了"改前基线"用旧的 pidfile 形状密集跑一轮全量门禁。
2. **门禁之间做残留清点**：每个站点验证前后对比存活的 `orchestratord`/fixture 进程数与 `$TMPDIR` 下目录数，净增长非零即停下处理，不带病继续。
3. **复现探针跑完立即显式回收**它故意留下的假守护进程，回收动作与探针成对出现在同一脚本里。
4. **监控磁盘水位**：会话开始与每完成一批站点后记录 `df` 输出；可用空间显著下降是停下的信号，不是事后解释的素材。

## 需求

### 1. 一个共享的守护进程拆解契约

把「停止守护进程并确认它真的停了」变成一处实现，而不是 25 份各自演化的副本。至少要满足：

- **等待要真的等**。不能依赖 `wait` 对非子进程生效；用轮询 `kill -0` 直到进程消失或超时。
- **超时后升级**。SIGTERM → 宽限期 → SIGKILL，与产品侧 FR-159 为 session 选的策略一致。
- **失败要具名**。守护进程没在宽限期内退出是一条要打印的事实，不是静默继续。

`scripts/lib/` 已有 `gate_runlog.sh`、`gate_jq.sh` 等先例；本项应作为库文件进入 `qa-gate-surface.json` 的 `supportFiles`（FR-158 已把 `scripts/lib/*` 纳入治理面，新文件会被 check 1 强制声明）。

### 2. 迁移 25 个站点，按 enforcement 排序

先 3 个 ci-required（它们能染红 CI），再 22 个 manual-runbook。**逐个验证要靠跑，不靠读**——FR-158 有一次教训：六个门禁的 source 行被 perl 写坏，`bash -n` 全过，六个门禁一次都没跑过就提交了。

### 3. 决定进程组回收的归属，并写下理由

FR-159 在 `test-agent-session-control-plane.sh` 里按进程组回收 session。需求 1 只解决「守护进程本身是否真的退出了」，不解决「它派生的东西是否还活着」。两者是不同的契约，本 FR 必须明确选择其一：

- (a) 共享库只管守护进程，session 回收留在需要它的门禁里；
- (b) 共享库同时管进程组。

**倾向 (a)**，理由：进程组回收需要门禁自己记录 session PID（`test-agent-session-control-plane.sh` 正是这么做的），这是门禁的领域知识，不是通用拆解逻辑。但这是一个要写下来的决定，不是默认。

### 4. 一条阻止第 26 个的棘轮 —— 且必须先回答它是否该存在

FR-158 立的规则要求任何新 ci-required 门禁写明它对应 §4.4 的哪个 shape。本项的候选答案是 **shape 9**（局部修复被记成全局）与 **shape 2**（没有任何东西让其余站点保持为真）。

但 DD-172 同样要求先问「这该不该是一道门禁」。**替代方案必须被认真评估**：如果需求 1 的库是唯一取得守护进程 PID 的途径，那么绕过它需要刻意为之，可能不值得再加一道 CI 门禁——治理预算当前是 1793s/2700s，余量 907s。**本需求的产出可以是「决定不加门禁」，只要理由成文。**
