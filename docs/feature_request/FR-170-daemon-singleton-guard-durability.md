# FR-170: 单例守卫把证据存在它必须幸存的那个目录里

## 优先级: P2

## 状态: Proposed

## 背景

计数与实测 at `b1a6a0d0`，方法注明；治理时 step 0 重建。

FR-169 治理期间实测到脑裂：删除数据目录后重建同名路径，旧守护进程仍活着并对
已 unlink 的数据库持有 7 个打开的 fd，而**第二个守护进程在同一路径上启动并
就绪**。FR-169 让旧进程约 15s 后自己退出，把窗口收敛到那 15s，
**并未消除它**（[DD-185](../design_doc/orchestrator/185-daemon-data-dir-vanish-self-termination.md)
的第一条已知限制）。本 FR 是那条限制。

### 放行第二个守护进程的链条（逐段实测 at `b1a6a0d0`）

1. 单例守卫是 `detect_running_daemon(&pid_path)`
   （`crates/daemon/src/main.rs:346`），它读的是
   `pid_path = data_dir/…`——**证据存在数据目录内部**；
2. 数据目录被删 → pidfile 随之消失 → 守卫读到"无人在运行"；
3. 守卫放行后，`crates/daemon/src/main.rs:1094` **无条件**
   `let _ = std::fs::remove_file(&socket_path)`（注释写的是"Remove stale
   socket"），随后 bind——**socket 同样不能充当占位证据**，因为下一个进程会先
   把它删掉；
4. 于是两个守护进程同时活着，其中一个不可见。

第 3 步不是多余的细节：`main.rs:343-345` 的注释明说 pid 检查的作用正是
"prevent socket destruction when multiple daemons race to bind the same UDS
path"。**socket 由 pidfile 守护，而 pidfile 由数据目录守护，数据目录没有任何
东西守护。** 一条三节的链子，最后一节接在空气上。

### 为何这不是 FR-169 的一部分

FR-169 的主语是"守护进程发现自己已不可能服务"，判据在自己身上，作用域封闭。
本 FR 的主语是"两个进程之间谁有权占据这个路径"，这需要一个**在数据目录之外
仍然可证的事实**，而那个事实存在哪里没有显然答案。治理时 FR-169 明确把它切出去，
理由记录在案：一个 FR 一个裁决。

## 需求

### 1. 先裁决目标，再谈机制

**本 FR 最先要回答的不是"用什么锁"，而是"要不要拦"。** 有两种读法，方向相反：

- **(a) 第二个守护进程本就该被允许启动。** 数据目录被删又重建，等于一个全新的
  状态目录；新进程接管它是合理的，真正的病是**旧进程还活着**。若取此读法，本 FR
  的正确产出是把 FR-169 的 ~15s 窗口压得更小（或让旧进程在更早的信号上退出），
  而不是加锁。
- **(b) 同一路径同时只能有一个守护进程，无论目录经历过什么。** 若取此读法，就需要
  一份数据目录之外的证据。

不得跳过这一裁决直接实现锁。§4.4 反复出现的形态是"给一个未经裁决的目标造一个
可观测性很好的机制"。

### 2. 若取 (b)：证据必须在数据目录之外可证

要求给出的机制满足：数据目录被 `rm -rf` 之后，一个**新**进程仍能判定
"另一个守护进程正持有这个 data_dir 路径"。

已清点的候选与各自的代价（治理时须逐一核验，本 FR 只标注方向）：

| 候选 | 问题 |
|---|---|
| `flock` 一个锁文件 | 若锁文件在 `data_dir` 内，与 pidfile 同病；树中**无 flock 先例**（`grep flock` 在非测试代码为零） |
| 抽象命名空间 socket | Linux-only，macOS 无此概念，而本仓库在两者上都跑 |
| 固定 OS 位置按 data_dir 路径散列的锁 | 引入一个新的全局路径概念，且路径别名（symlink、`/tmp` vs `/private/tmp`）会让同一目录散出两个键 |
| 扫描进程表找持有者 | 把守卫变成"是否有进程恰好打开了某个 inode"的推断，且需要遍历权限 |

**未核验**：以上四条均未实测，代价栏是阅读得出的判断而非测量。

### 3. 无论取 (a) 还是 (b)，`remove_file(&socket_path)` 的无条件性须复核

`main.rs:1094` 在 bind 前无条件删除既有 socket。它今天由 pidfile 守卫兜底；
若守卫的前提改变，这一行的正确性须重新论证，而不是继承。

## 验收标准

- [ ] 裁决 (a)/(b) 被写进设计记录，含**被否定那一侧的理由**——两种读法都自洽，
      只记录选中的一侧会让下一个读者无法判断这里是否想过
- [ ] 若取 (b)：`rm -rf data_dir && mkdir data_dir` 之后启动第二个守护进程，
      **被拒绝并具名**；断言诊断字符串而非退出码
- [ ] 若取 (a)：旧守护进程退出的窗口被实测并记录，且新进程接管后**旧进程的
      数据库 fd 归零**（FR-169 的探针已给出 7→0 的测法，复用）
- [ ] 负夹具：正常重启（先停后启，目录未变）不得被新机制拒绝——这是最容易被
      新守卫误伤的路径，且它每天都在跑
- [ ] 负夹具：`--foreground` 与 daemonize 两种启动形态给出同一答案
- [ ] 若引入锁文件：锁持有者被 SIGKILL 后，下一个进程**不得**被永久挡在门外
      （陈旧锁的释放语义须被断言，而不是依赖 OS 行为的口头描述）

## 依赖与关联

- [DD-185](../design_doc/orchestrator/185-daemon-data-dir-vanish-self-termination.md)
  已闭环机器侧的一半（旧进程自己退出）；本 FR 处理窗口内的重叠。
- [DD-174](../design_doc/orchestrator/174-qa-harness-daemon-teardown.md) 记录了
  最初暴露这条链子的泄漏。
- `detect_stale_pid` 已存在（`lifecycle.rs:154`），处理的是"pidfile 在但进程已死"；
  本 FR 处理的是相反的一半——"进程在但 pidfile 已不在"。二者是同一张表的两格，
  治理时应一并看，避免第三个函数各管一格。

## 概念预算（`CONTRIBUTING.md`）

若取 (a)，净增为零。若取 (b)，可能引入一个新的持久化物（锁文件或等价物）与一个
新的启动期失败模式，二者都是永久表面；治理时须论证为何它不能是既有 pidfile 的
一个字段或一次语义修正。**在裁决 (a)/(b) 之前不得开始铸造概念。**

## 未核验项（明确标注）

- **上表四个候选机制的代价均未实测**，仅为阅读判断。
- **窗口的实际危害未测量**：FR-169 之后重叠期约 15s，两个守护进程同时对**不同**
  数据库（一个孤儿、一个新建）写入。会不会产生用户可见的错误，未测。
- **是否存在第三种进入脑裂的路径未清点**：本 FR 只走了"删除数据目录"这一条；
  数据目录被 `mv` 走、被替换为 symlink、或所在卷被卸载后重挂，未测。
- **`slack-gateway` 是否有同形的单例守卫未清点**。
