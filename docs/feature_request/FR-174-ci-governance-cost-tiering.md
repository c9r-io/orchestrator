# FR-174: PR 反馈延迟由治理决定 —— 关键路径 24 分钟，其中产品验证 5 分钟

## 优先级: P2

## 状态: Proposed

## 背景

计数取自 `config/governance/ci-step-cost.json`（run `31398849814`，
head `ab98d6ff`），非本次实测。该文件自陈其中两条已删除步骤的秒数仍计入
所属 job 总数，故治理侧的数字**偏高**，方向对读者不利的那一侧 —— 本 FR
的论点在偏高被修正后依然成立，但幅度会变小。

`ci.yml` 十二个 job 中只有一条 `needs` 边（`boundary-coverage` 依赖
`coverage-policy-fixtures`），其余并行。因此 PR 的反馈延迟等于最长 job，
而不是秒数之和：

| job | 秒 | 性质 |
|---|---|---|
| **governance** | **1444** | 治理 |
| ci-environment-parity | 580 | 治理 |
| boundary-coverage（+ 前置 18） | 393 | 治理 |
| test | 321 | 产品 |
| clippy | 155 | 产品 |
| coordination-strangler | 126 | 治理 |
| cross-compile | 78 | 产品 |
| miri | 73 | 产品 |
| 其余四个 | 46 | 混合 |

- 关键路径 = `governance`，**1444 秒 ≈ 24 分钟**
- 产品验证（test + clippy + miri + cross-compile + fmt）合计 634 秒，
  其中最长的 `test` 是 **321 秒 ≈ 5.4 分钟**
- 治理类 job 合计 2578 秒，占全部 runner 时间的 **80%**

`ci-step-cost.json` 的预算（DD-153）约束的是 `governance` + `ci-environment-parity`
的**绝对秒数**上界 2700，当前 2024，未越界。本 FR 不主张预算失效 ——
预算做了它承诺的事。本 FR 主张的是预算**没有约束的那个量**：治理占关键
路径的比例。绝对上界回答「治理会不会失控」，它不回答「一个两行的改动
要等多久才知道自己对不对」。今天这两个问题的答案分别是「不会」和「24 分钟」。

`governance` job 内 48 个步骤，最贵的四个：

| 步骤 | 秒 |
|---|---|
| Verify gate enforcement surface **negative fixtures** | 241 |
| Core crate boundary and schema snapshot | 179 |
| Persistence crate extraction contracts | 155 |
| Agent driver execution migration contracts | 154 |

最贵的一步是**验证门禁能挡住东西的门禁**。这类 `* negative fixtures` 步骤
在 job 内成对出现近十次。它们的方法论是对的 —— DD-181 的双向棘轮、
§4.4 shape 1 对「文本存在性代理」的禁令，都要求门禁自身被变异验证过，
否则一个恒绿的门禁比没有门禁更糟。**本 FR 不主张削弱它们，主张改变它们
运行的时机。**

区别在于两类检查回答的问题不同：

- 「这个 PR 破坏了产品吗」—— 必须在 PR 上回答，因为答案随每次改动变化。
- 「这个门禁还能挡住它声称要挡的东西吗」—— 答案只在**门禁自身**被改动
  时变化。对一个不触碰 `scripts/qa/**` 的 PR 跑全套反例夹具，是在验证
  一个这次改动不可能影响的属性。

## Step 0 复核（2026-08-19，治理开工前）

本节由 fr-governance Phase 2 step 0 写入。**论点成立，四条支撑不成立。**

**方法**：`ci-cost.rb --refresh`（只读，未 `--write`）取 run `32099510921`
（head `e6081c6d`）。`ci.yml` 自 `e6081c6d` 起未变更，故这组数字描述当前树。
原数字取自 run `31398849814`（head `ab98d6ff`，2026-08-10），已落后 187 个提交、
6 次 `ci.yml` 变更。

| 论断 | 原文 | 实测 | 结论 |
|---|---|---|---|
| 关键路径 = `governance` | 1444s ≈ 24 分 | **1335s ≈ 22.3 分** | 成立，幅度变小 |
| 最长产品 job（`test`） | 321s | **324s** | 成立 |
| 治理类占比 | 80% | **78.9%**（2485/3148） | 成立 |
| 预算对（gov+parity） | 2024 / 2700 | **1912 / 2700** | 成立 |
| `governance` 步骤数 | 48 | **54**（6 步无测量） | 更正 |

**更正 1 —— 本 FR 只记录了自身测量误差的一个方向。** 背景段指出 188 秒已删除步骤
仍计入（偏高），据此断定治理侧数字偏高。但同时有 **6 个步骤完全没有测量值**
（偏低），六个都在 `ci.yml` 里，其中 `Rollback contract fixtures` 现测得 144s。
净值是 −109s，但撰写时无从知道符号。这是 §4.4 shape 9 出现在本 FR 自己的背景段里：
「一个缺陷会朝数据选择的方向失败，而你观察到的那个实例挑了一个方向」。

**更正 2 —— 本 FR 称赞的预算当时是关闭的。** 原文写「预算做了它承诺的事」。
门禁自己的输出是：

```
governance + ci-environment-parity = 2024s recorded against a 2700s budget, NOT ENFORCED:
  'Rollback contract fixtures' has never run and has no measurement
  ...（共 6 条）
```

DD-153 的 `pendingMeasurement` 一节就是这么设计的：一个已知缺步骤的总数不拿去和
上界比。这个 fail-safe 本意是短暂的 —— 该文件历史上每一次这样的窗口都在 0–1 天内
关闭。**这一次自 2026-08-11 起连续开了 8 天、5 个提交**，条数 2→3→4→6，因为
FR-163/FR-165 落地后没有人跑 `--refresh --write`。本 FR 写于 2026-08-17，正在这个
窗口的第 6 天。一次 `--refresh --write` 就能把它重新武装到 1912/2700 —— 而 step 0
本来就要求这次刷新。

**更正 3 —— 元验证的占比远大于原文所述，这一条是加强而非削弱。** 原文说
`* negative fixtures` 「近十次」。实测：**19 个步骤，合计 561 秒，占 `governance`
1335 秒的 42%**。移出后关键路径为 **774 秒 ≈ 12.9 分**。

**更正 4 —— 验收标准 3 犯了本 FR 背景段自己警告过的类别错误。** 背景把原则写对了：
「反馈延迟等于最长 job，而不是秒数之和」。验收标准 3 随即要求把分层后的关键路径
与「634 秒的产品验证下界」对照 —— 但 663 秒（当时 634 秒）是**五个并行 job 的和**，
它不是任何关键路径的界。可比的量是最长的那个产品 job，**324 秒**。而真正的结构下界
两者都不是：`governance` 即使归零，关键路径也会落在
**`ci-environment-parity` 的 577 秒**上。诚实的链条是
**1335 → 774（本 FR）→ 577（parity 下界）→ 324**。验收标准 3 已按此改写。

**收益前提实测。** 分层触发条件必须够罕见才值得建。最近 39 次并入 `main` 的合并中，
**9 次触及 `scripts/qa/**`、`scripts/lib/**` 或 `config/governance/**` —— 23%**。
即 77% 的 PR 走快路径，期望关键路径 ≈ 0.77·774 + 0.23·1335 = **903 秒**。

**治理裁决**：需求 3 采用「不设两级，只做 nightly + 触发式」——
仓库内不存在任何 `merge_group` 触发器，也不存在定时 CI workflow，合并队列需要改动
分支保护。范围限于 `governance` 的 19 个元验证步骤；`ci-environment-parity`
作为实测的下一个下界写入设计文档，其「第三类」问题陈述而不解决。

## 需求

### 1. 按「答案何时会变」分层，而不是按「重要性」分层

分层规则必须能从 PR 的变更集派生，且**失败关闭**：变更触及门禁自身
（`scripts/qa/**`、`scripts/lib/**`、`config/governance/**`）时，全套元验证
在 PR 上运行；否则移至合并前或 nightly。

「按重要性排序然后砍掉不重要的」是错的做法，会退化成对每个门禁的主观
辩论。按「这次改动能否影响该属性」派生则是机械的。

### 2. 移出 PR 路径的每一步都必须在别处真的跑

这是本 FR 最容易失败的地方，且这个仓库有先例：DD-159 记录过 WP05 门禁
**自 2026-03-26 起已死**却无人察觉，因为它在第一个场景之前就退出了。
一个被移到 nightly 但 nightly 从未成功运行的门禁，比留在 PR 上慢 24 分钟
糟得多 —— 前者把「未验证」呈现为「已通过」。

因此：分层的验收对象是「移出的步骤在新位置产生了可核验的执行证据」，
不是「PR 变快了」。`ci-job-liveness.json` 已有的活性机制是这条的现成载体。

### 3. 合并队列的裁决

若采用「PR 跑产品验证、合并前跑全套」的两级结构，需要裁决主分支被推入
未经全套治理验证的代码的窗口有多长、由什么关闭。可接受的答案包括
「不采用两级，只做 nightly + 触发式」。

### 4. 报告分层后的关键路径

分层后重新测量并写入 `ci-step-cost.json`，同时**新增一个记录关键路径的字段**
—— 当前该文件只记录 per-job 与 per-step 秒数，关键路径要靠读者自己
从并行结构推。本 FR 的整个论点依赖那个推导，说明它值得被直接记下来。

## 验收标准

- [ ] 分层规则从变更集派生并失败关闭；反例 fixture 覆盖
      「改动 `scripts/qa/**` 时元验证确实回到 PR 路径」
- [ ] 每一个移出 PR 路径的步骤在新位置有执行证据，且纳入
      `ci-job-liveness.json` 的活性检查
- [ ] 分层后 PR 关键路径秒数可报出确切数值，并与**最长的那个产品 job**
      （`test`，324 秒）对照说明差距来自什么。**不与产品 job 的秒数之和对照** ——
      并行 job 的和不是任何关键路径的界，见 step 0 更正 4。同时记下真正的结构
      下界是 `ci-environment-parity` 的 577 秒，以及分层为什么到不了 324 秒
- [ ] `ci-step-cost.json` 记录关键路径，且 DD-153 的预算条款按分层后的
      结构复核（预算若继续只约束绝对秒数，写明为什么这仍然够）
- [ ] 门禁**总数不减少**（负向验收：证明这是调度改变，不是覆盖削减）
