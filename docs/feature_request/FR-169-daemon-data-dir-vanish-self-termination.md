# FR-169: 数据目录消失后守护进程不自证死亡 —— 22 小时、零日志、服务零客户端

## 优先级: P2

## 状态: Proposed

## 背景

计数与实测 at `1d09a685`，方法注明；治理时 step 0 重建。

2026-08-12 一次探针脚本的 teardown 打错了 PID，两个 `orchestratord` 因此被
遗留（PID 37254/37273）。它们**存活 22 小时 34 分**，直到有人去看才被发现。
起因已定案且与本 FR 无关（`~/.claude/jobs/9883500f/tmp/t1-archive-check.sh`
的 `$!` 捕获缺陷，见
[DD-174](../design_doc/orchestrator/174-qa-harness-daemon-teardown.md)），
CLAUDE.md 已就该形状立规。

本 FR 的主语不是"谁启动错了"，而是**守护进程自己在那 22 小时里做了什么**：

- 它的数据目录（`$TMPDIR/t1-archive.sM2A1X/{a,b}`）在它脚下被 `rm -rf` 删掉；
- 它继续持有已 unlink 的 `agent_orchestrator.db`、`-wal`、`-shm` 三个 inode
  （证据：清点时的 `lsof`，见 `orphan-evidence/lsof-37254.txt`）；
- 它的 UDS socket 随目录一起消失，故**没有任何客户端能连上它**；
- 它没有退出，也没有说一个字。

### 实测（隔离环境，不触碰 `~/.orchestratord`）

`scratchpad/datadir-vanish-probe.sh`，at `1d09a685`，启停经由
`scripts/lib/gate_daemon.sh`：

| 观测 | 结果 |
|---|---|
| 删除数据目录后守护进程存活 | t+2/5/10/20/30s **全部 ALIVE** |
| 删除后写入日志的字节数 | **0**（日志大小自 t+2s 起冻结在 413 字节） |
| CLI 可达性 | `task list` **无法连上** |
| 退出 | 未发生 |

即：**一个已经不可能服务任何人的进程，无限期地活着，并且不说。** 22 小时那次
不是极端值，是这个行为的自然结果——没有任何机制会让它停。

### 为何这值得单独治理

FR-160 治理的是"调用方是否正确停止守护进程"，其边界按构造是 `scripts/**`；
DD-174 已记录残余：同一套工具在仓库之外（`~/.claude/jobs/**`）写的脚本是第二
个不受治理的产地，CI 永远看不到那里。**任何"教调用方做对"的措施都只覆盖你能
看见的调用方。** 本 FR 换一侧下手：让守护进程自己对"我的数据目录没了"负责，
从而对**所有**产地生效，包括尚未写出来的那些。

这也是 §4.4 的老问题换个位置：守护进程是否活着，是关于**机器**的事实；门禁的
作用域谓词是关于**仓库**的事实。只有机器一侧的措施能覆盖机器一侧的事实。

## 需求

### 1. 检测的是身份，不是路径存在性

`[ -d "$data_dir" ]` 是代理量。真正要问的是**"我当初打开的那个目录，现在还在
那个路径上吗"**——删除后重建同名目录时，路径存在为真，而守护进程正在写一个
孤儿 inode，同时新守护进程占着同一个路径。两种故障都必须被同一个判据捕获。

要求：启动时记录数据目录的 `(dev, ino)`，周期性重新 `stat` 并比较；不相等或
`stat` 失败即判定数据目录已消失。**不得**以路径存在性作为唯一判据。

### 2. 判定后自证死亡：具名退出，非静默

要求打印一条**点名机制**的日志（数据目录的路径、启动时与当前的 `(dev, ino)`、
判定的连续观测次数），然后以一个与正常关停可区分的退出码退出。今天的行为是
零日志——任何"它为什么没了"的事后追问都必须能在日志里得到答案。

### 3. 迟滞，因为误杀比漏杀贵

单次 `stat` 失败即退出会把瞬时故障（网络文件系统抖动、备份工具的原子替换）
变成生产事故。要求连续 N 次观测一致才判定，N 与周期均可配置；默认值须在治理
时**实测选取并记录余量**（§4.4 shape 11：先打印分布再选阈值，不要先选常数）。

### 4. 与既有关停路径共用一条退出序列

守护进程已有关停路径（`lifecycle` 的 socket/pidfile 清理，`shutdown_rx` 广播）。
自证死亡**不得**另写一条退出序列——那正是 FR-142/DD-150 与 FR-168 反复处理的
"两条语句序列"问题。注意此路径的特殊性：数据目录已经不在，故 socket/pidfile
的清理必然失败，且**这是正常的**，不得被记成错误。

## 验收标准

- [ ] 删除数据目录后，守护进程在 ≤(周期 × N + 余量) 内退出；断言的是**进程退出
      与那条具名日志**，不是退出码本身（退出码无法把本机制与任何其他失败区分开，
      §4.4 shape 7）
- [ ] **删除后重建同名目录**的场景：守护进程同样退出，且日志点明是 inode 变化
      而非路径缺失。这条是需求 1 与"路径存在性"实现的分界线——只做路径检查的
      实现在这条上必然绿转红
- [ ] 负夹具：数据目录**始终存在**的守护进程，在同等时长内**不得**退出（防止
      措施本身变成随机杀手）
- [ ] 负夹具：`stat` 单次瞬时失败后立即恢复，守护进程**不得**退出（需求 3 的
      迟滞真的存在，而不只是写在文档里）
- [ ] socket/pidfile 清理在数据目录缺失时的失败**不产生 error 级日志**，且不
      阻止退出
- [ ] 阈值选取的分布被记录在 DD 中，含余量（§4.4 shape 11）

## 概念预算（`CONTRIBUTING.md`）

本 FR **不新增** `ResourceKind`、顶层命令组或任何用户可见名词，故不铸造新的
`control_action_audit` 动作名。它新增的是守护进程的两个启动参数（周期与连续
观测次数），是既有 `orchestratord` 参数面上的字段而非新概念。

治理时须回答一个尚未裁决的问题：**这两个参数是否应该存在。** 无条件启用、不
可配置是更小的表面；可配置的理由只有"迟滞默认值可能对某些文件系统不合适"，
而该理由在实测分布出来之前只是猜测。若余量足够宽，正确的做法是**不加参数**。

## 未核验项（明确标注）

- **除数据目录外，是否还有等价的"我已不可能服务"信号未清点。** socket 文件被
  单独删除、数据库文件被单独删除、数据库被 `VACUUM` 之外的方式截断——这三种
  今天各自会怎样，未测量。本 FR 只测了整目录删除这一种。
- **真实 `~/.orchestratord` 上的行为未测**，且不应以破坏性方式测。实测全部在
  隔离数据目录上进行，故"生产守护进程遇到同样情况也如此"是推断而非观测。
- **周期/迟滞的默认值未选取**，需求 3 要求治理时实测。本 FR 不预设数字。
- **本类缺陷是否还有第二处实例未清点**：`slack-gateway` 拥有自己的数据库
  （`persistence-dependency-ledger.json` 的 `separate-database` 角色），它对
  自身数据目录消失的反应未测量。形状可泛化，裁决不可。
