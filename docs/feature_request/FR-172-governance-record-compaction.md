# FR-172: 治理记录只增不减 —— 闭环尾注 17 倍膨胀与 superseded 文档的无限留存

## 优先级: P1

## 状态: Proposed

## 背景

计数 at `c6dbc5d7`。方法：对 `docs/feature_request/README.md` 按生成标记切分后
逐条测量；文档存量由 `doc-lifecycle.rb` 治理的三个根目录派生。单一派生，
未经 step 0 重建。

这个仓库对**文档漂移**有治理（FR-132/DD-144 的 `lifecycle` 字段），对**文档
增长**没有。两者的区别是：漂移治理回答「这份文档还成立吗」，增长治理回答
「这份文档还值得被读吗」。第二个问题目前无人问，于是记录面单调增长。

### 证据 1：闭环尾注已占 FR README 的 90%，且单调膨胀

`docs/feature_request/README.md` 共 394 行 / 192,933 字节，构成为：

| 段 | 行 | 字节 | 占比 |
|---|---|---|---|
| 序言 | 7 | 1,432 | 0.7% |
| 生成的注册表（`fr_registry.rb` 从 HEAD 祖先历史派生） | 170 | 17,451 | 9% |
| **人工闭环尾注** | **216** | **174,050** | **90%** |

171 条尾注，单条长度 min 75 / median 332 / **max 11,378** 字符。按 FR 编号
分桶后是一条单调曲线：

| 区间 | 条数 | 平均字符 |
|---|---|---|
| FR-000..019 | 17 | 212 |
| FR-060..079 | 18 | 280 |
| FR-100..119 | 21 | 402 |
| FR-120..139 | 23 | 1,083 |
| FR-140..159 | 22 | 2,918 |
| FR-160..179 | 9 | **3,608** |

**尾注的职责是重定向，不是复制。** 最早的形态就是它该有的形态：
「FR-XXX 已闭环删除；其设计与验证信息现由 DD-N 与 QA-M 承载」——
一个指针，把读者送到承载文档。后期的尾注则把治理过程中的裁决、更正、
反例、已知限制整段写进 README，而这些内容**同时也在** DD 里。于是同一
份事实有两个副本，其中一个躺在一个没人会通读的 193KB 文件里，且它不受
`doc-lifecycle.rb` 治理（该门禁的 `DOC_ROOTS` 是 design_doc/qa/security，
不含 feature_request），也就是说**它永远不会被标记为过时**。

机制是被规定的：`.claude/skills/fr-governance/SKILL.md:240` 要求每次闭环
「Add a closure note following the existing pattern」。"existing pattern" 在
2026-03 指的是那句 212 字符的指针，今天指的是 3,608 字符的复盘 —— 规则文字
没变，它所指的先例变了。这是追加型规则的典型失效方式。

### 证据 2：superseded 文档只标记不退役

`doc-lifecycle.rb` 治理 487 篇文档：**472 active / 15 superseded**（数字取自
门禁自身的输出，不是 grep —— 按 `lifecycle: superseded` grep 会多数出两篇，
因为有文档在正文里讨论这个字段）。
`superseded` + `superseded_by` 让读者能从过时文档导航到继任者（这是 FR-132
的正确设计，不动它）。但没有任何规则说 superseded 文档**何时可以删除**。
15 篇今天不构成负担；问题在于速率没有上界，而每一篇都进入
`config/governance/doc-lifecycle-index.json`（3,167 行）并被每次门禁运行读取。

DD-159 已经论证过一件相关的事：superseded 文档不适用「示例必须可粘贴运行」
的前提。这说明 superseded 已经是一个**受降级对待**的状态 —— 那么「降级到
什么程度算可以移除」就是一个能被回答的问题，而不是一个开放式的哲学问题。

## 需求

### 1. 闭环尾注恢复为指针，并给出容量规则

- 规则的形状是**每条尾注的上界**，不是文件总量上界 —— 后者会让最后一条
  尾注为前面 170 条的膨胀买单，这不公平也不可执行。
- 上界应当从尾注的职责派生并写明理由，而不是取当前分布的分位数（FR-140
  禁止用实测值反推阈值：实测是样本，不是函数）。职责是「让读者找到承载
  文档，并知道该 FR 是否有超出承载文档的裁决」，据此选一个数并说明它为
  什么够用。
- **超出上界的内容归位到 DD，而不是删除。** 本 FR 不主张丢失任何裁决记录；
  它主张记录只存一份，且存在受 `lifecycle` 治理的那一份里。
- `fr-governance` skill 的 `SKILL.md:240` 改为引用规则本身，而不是引用
  「existing pattern」—— 后者是一个会漂移的指代。

### 2. 存量压实

171 条尾注按规则压实。这是本 FR 的主要交付物，且**必然是净删除**。
被移出的内容中，凡在对应 DD 里查无实据的，先补进 DD 再从 README 移除；
凡已在 DD 里的，直接移除。两种情况都要留下可核验的对应关系。

### 3. superseded 文档的退役窗口

给 `lifecycle: superseded` 定一条退役规则并进入 `doc-lifecycle.rb`。裁决
可以是「不退役，理由 X」—— 但必须成文，因为当前状态是**没有人做过这个决定**，
而不是有人决定了保留。

若决定退役，删除前的条件至少应包括：`superseded_by` 链条仍可解析（删掉中间
一环会让入边悬空），且没有 active 文档引用它。

### 4. 增长的可见性

治理面已有执行成本预算（`ci-step-cost.json`，DD-153），记录面没有对应物。
最小可行形态是让 `doc-lifecycle.rb` 在每次运行时打印治理文档的篇数与总字节，
使增长在日志里可见 —— 不设门槛，只使其可见。是否进一步门禁化，按 DD-172
之问裁决（预期答案：不门禁，因为「这份文档是否值得读」是判断，门禁只能
检查字节数这个代理量，即 §4.4 shape 1）。

## 验收标准

- [ ] `docs/feature_request/README.md` 净减少的字节数 > 0 且可报出确切数值；
      压实后每条尾注满足规则上界
- [ ] 从 README 移出的每一条裁决，在对应 DD 中可被指认（给出对应表，
      不是「已核对」这种自陈）
- [ ] 尾注规则写进 `fr-governance` skill，且 `SKILL.md` 不再用
      「existing pattern」指代规则
- [ ] superseded 退役规则成文；若采纳退役，`doc-lifecycle.rb` 增加悬空
      `superseded_by` 的检查并配反例 fixture
- [ ] `doc-lifecycle.rb` 输出文档篇数与总字节
- [ ] 全部文档门禁绿；`fr_registry.rb` 的生成块与标记未被破坏（压实只动
      END 标记之后的人工段）

## 未核验项（明确标注）

- 尾注与 DD 的内容重合度**未测量**。本 FR 断言「同一份事实有两个副本」，
  依据是抽读 FR-168/169 两条尾注与 DD-184/185 的对照，不是全量比对。
  需求 2 的第一步应当是逐条比对，其结果可能显著改变工作量 —— 若大量裁决
  **只**存在于尾注而不在 DD 里，那么这不是压实工作，而是补写 DD 的工作。
- 分桶曲线以 FR 编号为横轴，编号近似但不等于时间序（FR 立项与闭环之间
  有间隔，且存在编号碰撞 5 例）。趋势方向可靠，斜率不精确。
- 15 篇 superseded 文档各自被多少 active 文档引用未清点，故需求 3 的
  退役可行性未知。
- 本 FR 未处理 `docs/qa` 的 274 篇存量本身。QA 文档同时是 `qa_targets`
  语料（自举时的 task item 来源），删除它们会改变运行时行为，属于不同
  性质的问题，另起。
